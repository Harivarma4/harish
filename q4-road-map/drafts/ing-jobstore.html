RETRY BY ITSELF

Data Platform Roadmap · 10c

This is the part of the ingestion platform that is already built, and it is what makes runs trustworthy. Every run is a job in PostgreSQL, split into one task per table or file, and every phase, watermark, validation result and metric is recorded against it. The API writes the job and puts one message per task on Redis; Celery workers pick tasks up and load them with dlt. A worker claims a task with a single conditional update, so even if Redis delivers the same message twice, only one copy runs. The orange parts are what the Q4 proof of concept added on top, so that six clients can run every day without anyone watching. A transient error, such as a timeout, a 429 or 5xx response or a deadlock, puts the task into RETRY_WAIT, and the scheduler re-queues it after one, two, then four minutes, up to thirty, for three attempts by default. A permanent error, like bad credentials or a missing table, fails at once and sends one alert. While a task runs, its worker writes a heartbeat every thirty seconds; if the heartbeat stops for ten minutes, the reaper takes the task back and runs it again. In the test we killed a worker in the middle of a 2.5 million row load and it finished on the second attempt 35 seconds later. Fencing on the attempt number means a worker that was only slow can never overwrite the newer result. So in Q4 we are not building the job store; we are hardening, hosting and operating it.
