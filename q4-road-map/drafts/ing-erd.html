Initiative 1 · Job store ERD

21 PostgreSQL tables, built around the pipeline

Data Platform Roadmap · 10e

This is the full entity relationship diagram of the job store, all 21 tables. Read it from the pipeline in the middle. A pipeline belongs to one connection, the source, and one target, where the files land. It has many pipeline objects, one per table or file it moves. Every run is a job, and a job has one task per pipeline object; that task is the unit a worker claims, and it carries the attempt number used for fencing. Events, metrics and validation results hang off jobs and tasks, so every run can be explained afterwards. Watermarks keep one value per object, for incremental loads. The orange tables came with the Q4 proof of concept in migration 0005: one optional schedule per pipeline, reconciliation specs and runs that compare our output with the legacy files, and alert channels with a delivery log whose unique dedupe key means one failure sends one alert. Two things to note: tenant_id is on every table but is a real foreign key only on users, and since each client runs its own copy with its own database, every row in one database belongs to the same client, and audit_events, uploads, templates and secrets have no foreign keys. Secrets is in the code but not used in Q4; credentials come from environment variables. The complete PostgreSQL definition, with every column, type, index and constraint, is in jobstore_schema.sql.
